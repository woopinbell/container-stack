# container-stack

직접 구성한 컨테이너 서비스의 경계와 운영 절차를 학습하기 위한 프로젝트다.
초기 단계에서는 구현보다 먼저 서비스 책임과 저장소 규약을 정의한다.

## 예정 범위

- Docker Compose로 단일 호스트의 서비스 토폴로지를 관리한다.
- nginx를 외부 요청의 TLS 진입점으로 둔다.
- WordPress는 PHP-FPM 애플리케이션 계층을 담당한다.
- MariaDB는 애플리케이션의 영속 데이터를 소유한다.
- 영속 데이터와 설정은 목적별 볼륨으로 분리한다.
- 런타임 비밀번호는 호스트의 `secrets` 파일에서 전달한다.

이 항목들은 개발 경계를 나타내며 아직 완성된 기능을 뜻하지 않는다.
각 서비스는 최소 실행 경로부터 차례로 추가한다.

## 저장소 규약

- 제품 이미지는 각 서비스의 Dockerfile에서 직접 구성한다.
- 공개 설정 예시는 추적하되 실제 비밀번호와 `.env`는 추적하지 않는다.
- 생성물, 로컬 캐시, 임시 진단 자료는 소스와 구분한다.
- 서비스가 소비하지 않는 미래 설정이나 경로를 미리 등록하지 않는다.
- 한 변경은 하나의 책임을 가지며 독립적으로 검토할 수 있어야 한다.
- 기능, 수정, 테스트와 문서는 가능한 한 분리한다.

## 검증 원칙

정적 계약이 준비되면 `make test`로 저장소 구성을 확인한다.
실행 가능한 요청 경로가 완성되면 `make smoke`로 HTTPS 응답을 확인한다.
Docker Compose 설정은 실제 기동 전에 렌더링하여 검사한다.

검증 명령이 아직 존재하지 않는 단계에서는 해당 파일을 미리 참조하지 않는다.
새 검증은 대응하는 구현 경계가 생긴 뒤 추가한다.

## 비밀값 원칙

- 비밀번호는 이미지, 환경 예시, 명령 인자에 직접 기록하지 않는다.
- 비밀 파일은 필요한 서비스의 초기화 단계에서만 읽는다.
- 애플리케이션과 데이터베이스 계정의 책임을 구분한다.
- 로그와 진단 결과에는 비밀값이 노출되지 않아야 한다.

구체적인 구성, 실행 및 복구 절차는 구현이 안정된 뒤 이 문서에 보완한다.
